### 1차 선정

**Re:Focus**를 최종안으로 선정한다.

- 복귀에 걸린 시간을 전후 비교하여 생산성 향상을 정량적으로 증명할 수 있다.
- 단순 요약이 아니라 수집, 계획, 실행, 검증의 에이전틱 루프를 명확히 보여준다.
- Copilot SDK가 업무 컨텍스트와 도구 실행에 직접 관여하므로 기술 활용이 장식에 그치지 않는다.
- Azure의 상태 저장, AI 추론, 관측 기능이 지속적인 업무 스레드 복원에 필수적이다.
- 모든 행동을 사용자가 승인하도록 설계해 책임 있는 AI와 신뢰성을 함께 보여줄 수 있다.

## 2. 문제 정의

### 대상 사용자

회의, 메신저, 문서 작업, 개발 업무를 오가며 하루에도 여러 번 집중이 끊기는 개인 지식 노동자.

### 핵심 문제

사용자는 중단된 업무로 돌아올 때 다음 내용을 다시 찾아야 한다.

- 마지막으로 무엇을 했는가
- 중단된 이유와 당시의 판단은 무엇이었는가
- 그사이 무엇이 바뀌었는가
- 지금 가장 먼저 해야 할 행동은 무엇인가

이 과정에서 여러 탭, 문서, 커밋, 이슈와 메모를 다시 읽으며 매번 10~20분의 비생산적인 복구 시간이 발생한다. 기존 요약 도구는 정보를 압축하지만 사용자가 실제로 일을 재개할 수 있는 다음 행동까지 연결하지 못한다.

### 해결 가설

업무 스레드의 마지막 상태와 변경 사항을 자동으로 모으고, 근거가 연결된 90초 복귀 브리프와 실행 가능한 다음 행동을 제시하면 사용자의 업무 복귀 시간을 80% 이상 줄일 수 있다.

## 3. 제품 개요

Re:Focus는 사용자가 작업을 중단할 때 **체크포인트**를 저장하고, 돌아왔을 때 관련 소스의 변경 사항을 조사해 **복귀 브리프**를 만든다. 사용자가 다음 행동을 승인하면 에이전트가 초안 작성, 이슈 업데이트, 작업 계획 생성 같은 안전한 작업을 수행하고 결과를 검증한다.

### 핵심 가치 제안

**“어디까지 했지?”를 찾는 대신 “여기서 계속”을 누른다.**

### 주요 개념

- **업무 스레드:** 목표, 관련 링크, 메모, 활동 기록을 묶은 작업 단위
- **체크포인트:** 중단 시점의 진행 상태, 미해결 질문, 다음 행동
- **복귀 브리프:** 마지막 상태, 이후 변경 사항, 의사결정, 위험, 추천 행동을 담은 근거 기반 요약
- **액션 플랜:** 사용자가 승인하거나 수정할 수 있는 실행 단계
- **증거 원장:** 에이전트가 판단에 사용한 출처와 실행 결과 기록

## 4. 핵심 사용자 흐름

1. 사용자가 새 업무 스레드를 만들고 목표와 GitHub 저장소·이슈 등 관련 소스를 연결한다.
2. 작업을 멈출 때 `체크포인트 저장`을 눌러 현재 상태와 미해결 질문을 남긴다.
3. 다시 돌아온 사용자가 `복귀 브리프 생성`을 누른다.
4. 컨텍스트 수집 에이전트가 체크포인트 이후의 커밋, 이슈, 메모 변화를 수집한다.
5. 계획 에이전트가 변경 사항을 비교하고 다음 행동 후보를 우선순위와 근거와 함께 제안한다.
6. 검증 에이전트가 누락, 근거 없는 주장, 위험한 행동을 검사한다.
7. 사용자는 제안을 승인, 수정 또는 거절한다.
8. 실행 에이전트가 승인된 작업만 수행하고 결과와 실패 상태를 증거 원장에 기록한다.
9. 대시보드가 복귀 소요 시간과 절약된 시간을 표시한다.

## 5. 에이전트 설계

### Copilot SDK의 역할

Copilot SDK는 제품의 핵심 런타임으로 사용한다.

- 업무 스레드별 지속 세션과 대화 컨텍스트 관리
- GitHub 저장소, 커밋, 이슈 등 개발 컨텍스트 조회
- 구조화된 복귀 브리프 및 액션 플랜 생성
- 도구 호출과 스트리밍 진행 상태 제공
- 승인된 GitHub 이슈 초안 작성 또는 업데이트

단순 질의응답 호출이 아니라 컨텍스트 수집과 실제 도구 실행에 SDK를 사용한다. 데모에서는 SDK가 호출한 도구, 입력 근거, 출력 결과를 화면에 노출한다.

### Microsoft Agent Framework의 역할

Microsoft Agent Framework는 전문 에이전트의 오케스트레이션과 상태 전달을 담당한다.

| 에이전트 | 책임 | 입력 | 출력 |
| --- | --- | --- | --- |
| Context Agent | 체크포인트 이후 변경 사항 수집·정규화 | 업무 스레드, 연결 소스 | 출처가 포함된 변경 목록 |
| Planner Agent | 현재 상태 재구성과 다음 행동 설계 | 체크포인트, 변경 목록 | 복귀 브리프, 액션 플랜 |
| Safety Agent | 근거, 권한, 민감정보, 위험 행동 검사 | 브리프, 액션 플랜 | 경고, 수정 요청, 실행 허용 범위 |
| Action Agent | 승인된 작업 실행 | 사용자 승인, 허용된 도구 | 실행 결과, 실패 정보 |
| Verifier Agent | 실행 결과와 목표 달성 여부 검증 | 계획, 실행 결과 | 검증 상태, 후속 제안 |

### 오케스트레이션 규칙

```text
Context → Planner → Safety → 사용자 승인 → Action → Verifier
				  ↘ 보완 필요 시 Planner로 1회 반환
```

- 에이전트 간 전달 데이터는 자유 형식 텍스트가 아닌 구조화된 스키마를 사용한다.
- Safety Agent를 통과하지 않은 액션은 사용자에게 실행 버튼을 제공하지 않는다.
- Action Agent는 사용자가 승인한 도구와 범위 안에서만 실행한다.
- Verifier Agent가 실패를 감지하면 자동 재실행하지 않고 원인과 재시도 선택지를 제시한다.

## 6. Azure 아키텍처

Azure는 단순 배포 대상이 아니라 상태 유지와 신뢰성의 핵심으로 사용한다.

| Azure 서비스 | 역할 | 데모 증거 |
| --- | --- | --- |
| Azure App Service | Next.js 웹 앱과 API 호스팅 | 실제 배포 URL과 상태 화면 |
| Microsoft Foundry 모델 배포 | Agent Framework 에이전트의 추론 | 요청 추적 ID와 에이전트 실행 로그 |
| Azure Cosmos DB | 업무 스레드, 체크포인트, 승인, 증거 원장 저장 | 저장 전후 데이터와 세션 복원 |
| Azure Key Vault | 외부 서비스 자격 증명과 비밀 관리 | 환경 변수에 비밀이 없음을 구성으로 확인 |
| Application Insights | 지연 시간, 오류, 에이전트 단계 추적 | 데모 실행의 end-to-end trace |

### 핵심 데이터 모델

```text
User
└── WorkThread
	├── Source[]
	├── Checkpoint[]
	├── ResumeBrief[]
	├── ActionPlan[]
	└── EvidenceEvent[]
```

`WorkThread`를 Cosmos DB 파티션 키로 사용해 한 업무의 상태와 증거를 효율적으로 조회한다. 원본 문서 전체 대신 필요한 메타데이터와 출처 링크를 저장해 개인정보 보관 범위를 줄인다.

## 7. MVP 범위

### 반드시 완성할 기능

- 업무 스레드 생성, 목록, 상세 보기
- 중단 시 체크포인트 저장
- GitHub 저장소 또는 이슈 연결
- 체크포인트 이후 변경 사항 수집
- 근거 링크가 포함된 복귀 브리프 생성
- 다음 행동 1~3개 제안
- 사용자 승인 후 GitHub 이슈 초안 생성 또는 업데이트
- 실행 성공·실패와 에이전트 진행 상태 표시
- 복귀 시간 측정 및 절약 시간 대시보드
- Cosmos DB 상태 저장과 Azure 배포

### 시간이 남으면 추가할 기능

- Outlook 일정과 회의 메모 연결
- 여러 업무 스레드 간 우선순위 추천
- 반복되는 중단 원인과 집중 패턴 분석
- 브리프 공유 및 팀 인계

### 명시적 비범위

- 사용자 승인 없는 메일 전송, 코드 변경 또는 이슈 게시
- 범용 데스크톱 자동화
- 모든 업무 도구를 지원하는 통합 플랫폼
- 사용자의 생산성을 감시하거나 평가하는 관리자 기능

## 8. 화면 구성

### 오늘 화면

- 진행 중인 업무 스레드와 마지막 체크포인트
- `계속하기` 기본 행동
- 오늘 절약한 복귀 시간

### 업무 스레드 화면

- 목표와 현재 상태
- 체크포인트 타임라인
- 연결된 출처와 최신 변경 사항
- 에이전트 실행 단계와 상태

### 복귀 브리프 화면

- **마지막 상태:** 중단 전에 완료한 내용
- **그사이 변경됨:** 체크포인트 이후 달라진 내용
- **주의 필요:** 미해결 질문, 충돌, 위험
- **추천 다음 행동:** 근거, 예상 시간, 영향도
- 승인, 수정, 거절 컨트롤

### 증거 패널

각 주장과 행동 옆에서 출처 링크, 수집 시각, 에이전트, 도구 호출 결과를 확인할 수 있게 한다. 기술 데모와 사용자 신뢰를 같은 UI로 해결한다.

## 9. 생산성 검증 계획

### 핵심 지표

| 지표 | 기존 방식 기준값 | MVP 목표 | 측정 방법 |
| --- | ---: | ---: | --- |
| 업무 복귀 시간 | 15분 | 90초 이하 | 스레드 열기부터 첫 행동 승인까지 측정 |
| 다시 확인한 화면 수 | 6개 | 2개 이하 | 사용자가 연 출처 수 비교 |
| 다음 행동 결정 시간 | 5분 | 60초 이하 | 브리프 표시부터 승인까지 측정 |
| 근거 연결률 | 측정 없음 | 100% | 브리프의 주요 주장 중 출처가 있는 비율 |

### 검증 방식

동일한 GitHub 업무 시나리오를 두 번 수행한다.

1. **기존 방식:** 커밋, 이슈, 메모를 직접 탐색해 업무를 재개한다.
2. **Re:Focus 방식:** 복귀 브리프를 확인하고 추천 행동을 승인한다.
3. 소요 시간, 클릭 수, 누락된 변경 사항을 비교해 결과를 대시보드와 발표 자료에 표시한다.

## 10. 책임 있는 AI, 보안, 신뢰성

### 책임 있는 AI

- 모든 AI 생성 내용에 표시를 붙이고 출처를 함께 제공한다.
- 사용자는 제안을 승인, 수정, 거절할 수 있으며 언제든 실행을 중단할 수 있다.
- 근거가 없거나 충돌하는 내용은 사실처럼 단정하지 않고 `확인 필요`로 표시한다.
- 생산성 지표는 사용자 개인에게만 제공하며 성과 평가 점수로 사용하지 않는다.

### 보안

- 최소 권한 OAuth 범위와 사용자별 접근 제어를 적용한다.
- 비밀은 Key Vault에 저장하고 로그, 클라이언트 번들, 데이터베이스에 기록하지 않는다.
- 도구 입력을 스키마로 검증하고 프롬프트 인젝션이 의심되는 외부 텍스트를 명령으로 실행하지 않는다.
- 저장 데이터 삭제와 연결 해제 기능을 제공한다.

### 신뢰성

- 각 에이전트 단계에 타임아웃과 명시적 실패 상태를 둔다.
- 외부 API 오류 시 제한된 재시도 후 사용자에게 수동 재시도 옵션을 제공한다.
- 모든 실행에 idempotency key를 사용해 중복 이슈 생성을 방지한다.
- 에이전트 실행 전체를 Application Insights의 단일 trace로 연결한다.

## 11. 데모 시나리오

### 3분 데모

1. **문제 제시:** 어제 중단한 기능 개발 업무로 돌아왔지만 그사이 커밋과 이슈 댓글이 추가된 상황을 보여준다.
2. **체크포인트 확인:** 마지막 판단, 미해결 질문, 당시 다음 행동을 확인한다.
3. **에이전트 실행:** `복귀 브리프 생성`을 누르고 Context → Planner → Safety 단계와 도구 호출을 실시간으로 보여준다.
4. **결과 확인:** 변경 사항과 추천 행동마다 연결된 GitHub 근거를 연다.
5. **승인·실행:** 이슈 업데이트 초안을 수정하고 승인한 뒤 Action → Verifier 결과를 확인한다.
6. **효과 증명:** 복귀 시간, 클릭 수, 절약 시간을 기존 방식과 비교한다.
7. **Azure 증명:** Cosmos DB에 복원된 상태와 Application Insights trace를 짧게 보여준다.

### 실패 시나리오

권한이 없는 이슈 업데이트를 일부러 요청해 Safety Agent가 실행을 차단하고, 권한 부족 이유와 안전한 대안을 표시하는 장면을 준비한다.

## 14. 100점 목표 추가 아이디어: OneIntent

> 목표 한 문장을 검증 가능한 완료 상태로 컴파일하는 개인 업무 실행 에이전트

### 14.1 먼저 짚어야 할 점

아이디어만으로 100점을 받을 수는 없다. [SCORING.md](./SCORING.md)는 설명이 아니라 실행 가능한 데모, 코드, Azure 리소스, 측정 결과를 요구한다. 따라서 OneIntent의 100점은 예상 점수가 아니라 **모든 평가 항목에서 만점 증거를 만들기 위한 제품·구현 목표**다.

Re:Focus가 만점을 놓칠 가능성이 있는 이유는 다음과 같다.

- 사용자가 체크포인트를 직접 남겨야 하므로 생산성 효과가 입력 습관에 의존한다.
- 복귀 브리프는 강력하지만 기존 요약·업무 복원 제품과 비교해 독창성 설명이 더 필요하다.
- GitHub 중심 흐름은 개발자에게는 적합하지만 개인 지식 노동 전반의 문제로 확장하기 어렵다.
- 브리프 생성 후 외부 행동 하나만 실행하면 Agent Framework의 오케스트레이션 깊이가 약해 보일 수 있다.

OneIntent는 이 약점을 **실행 계약, 목표 그래프, 드라이런, 검증 영수증**으로 보완한다.

### 14.2 문제 정의

지식 노동자는 “내일 리뷰 준비를 끝낸다”와 같은 하나의 목표를 완료하기 위해 여러 도구를 오가며 반복 작업을 수행한다.

- 캘린더에서 참석자와 시간을 확인한다.
- GitHub에서 관련 PR과 미해결 이슈를 찾는다.
- 변경 사항과 위험을 요약한다.
- 리뷰 안건과 질문을 작성한다.
- 후속 작업을 만들고 공유 메시지를 준비한다.
- 빠진 내용이 없는지 다시 확인한다.

작업 하나하나는 어렵지 않지만 도구 전환, 정보 재탐색, 순서 결정, 결과 확인에 시간이 소모된다. 기존 챗봇은 답변이나 초안을 만들지만 사용자의 목표가 실제로 완료됐는지 검증하지 않는다.

### 14.3 해결책

사용자는 목표, 시간 예산, 실행 금지 범위를 한 번 입력한다.

```text
목표: 내일 결제 기능 리뷰 준비를 끝내줘.
시간 예산: 20분
허용: GitHub 조회, 리뷰 안건 초안, 개인 할 일 생성
금지: 메시지 전송, 코드 변경, 이슈 게시
성공 조건: 변경 요약, 위험 3개, 질문 목록, 30분 리뷰 일정안이 준비됨
```

OneIntent는 이 입력을 **실행 계약(Execution Contract)**으로 변환한다. 실행 계약은 목표, 성공 조건, 시간 예산, 필요한 도구, 권한, 예상 부작용을 포함한다. 이후 에이전트가 작업 의존성을 목표 그래프로 만들고, 실행 전 결과를 시뮬레이션한 뒤 사용자에게 한 번에 승인을 요청한다.

### 14.4 핵심 차별점

#### 목표를 답변이 아닌 테스트로 변환

“리뷰 준비”를 단순 요약 요청으로 처리하지 않고 다음과 같은 검증 가능한 성공 조건으로 변환한다.

- 관련 PR이 최소 1개 연결되어 있다.
- 모든 주요 주장에 출처가 있다.
- 위험 목록에 영향도와 대응 질문이 있다.
- 리뷰 안건의 총 예상 시간이 30분 이하다.
- 외부 전송이나 게시가 발생하지 않았다.

#### 목표 그래프

에이전트는 할 일 목록이 아니라 선후 관계와 성공 조건이 있는 실행 그래프를 만든다.

```text
목표 해석
├── 캘린더 제약 확인
├── GitHub 변경 수집
│   └── 변경·위험 분석
├── 리뷰 안건 생성
│   ├── 변경·위험 분석
│   └── 캘린더 제약 확인
└── 성공 조건 검증
	└── 리뷰 안건 생성
```

서로 독립적인 조회는 병렬로 실행하고, 선행 결과가 필요한 작업만 대기한다. 화면에서는 각 노드의 대기, 실행, 승인 필요, 성공, 실패 상태를 실시간으로 보여준다.

#### 드라이런과 변경 미리보기

실행 전에 “무엇을 읽고 무엇을 바꿀지”를 diff 형태로 보여준다. 사용자는 전체 계획을 한 번에 승인하거나 특정 노드만 제외할 수 있다. 쓰기 작업은 승인 이후에만 실행된다.

#### 검증 영수증

실행 후에는 자연어 완료 메시지가 아니라 다음 내용을 담은 검증 영수증을 제공한다.

- 성공 조건별 통과·실패 상태
- 사용한 출처와 도구 호출
- 생성되거나 변경된 항목
- 실행하지 않은 금지 행동
- 걸린 시간과 기존 방식 대비 절약 시간
- 재실행 가능한 실패 노드

### 14.5 대표 사용자 시나리오

**“내일 결제 기능 리뷰 준비를 20분 안에 끝내줘.”**

1. 사용자가 목표와 금지 범위를 입력한다.
2. Intake Agent가 모호한 성공 조건만 1회 질문한다.
3. Research Agent가 Outlook 일정과 GitHub PR·이슈를 병렬 조회한다.
4. Planner Agent가 목표 그래프, 예상 시간, 도구 권한을 구성한다.
5. Policy Agent가 프롬프트 인젝션, 과도한 권한, 외부 쓰기 작업을 검사한다.
6. 화면이 드라이런과 변경 미리보기를 표시한다.
7. 사용자가 계획 전체를 한 번에 승인하되 메시지 전송 노드는 제외한다.
8. Executor Agent가 승인된 노드만 실행한다.
9. Verifier Agent가 성공 조건을 검사하고 검증 영수증을 발급한다.
10. 사용자는 준비된 리뷰 팩을 내려받거나 업무 스레드에 저장한다.

### 14.6 Copilot SDK 및 Agent Framework 설계

#### Copilot SDK: 12.5점 만점 목표

- 목표별 지속 세션과 사용자 컨텍스트 관리
- GitHub 저장소, PR, 이슈를 조회하는 실제 도구 호출
- 구조화된 실행 계약과 목표 그래프 출력
- 에이전트 진행 이벤트의 웹 UI 스트리밍
- 사용자 승인 이후에만 허용되는 쓰기 도구 실행
- 도구 호출 입력, 결과, 출처를 검증 영수증에 연결

#### Microsoft Agent Framework: 12.5점 만점 목표

| 에이전트 | 역할 | 만점이 필요한 이유 |
| --- | --- | --- |
| Intake Agent | 의도, 시간 예산, 성공 조건, 금지 범위 구조화 | 모호한 요청을 실행 가능한 계약으로 바꿈 |
| Research Agent | GitHub·Outlook 컨텍스트 병렬 수집 | 실제 도구 사용과 병렬 오케스트레이션 증명 |
| Planner Agent | 의존성 있는 목표 그래프 생성 | 단순 체인보다 명확한 Agent Framework 활용 |
| Policy Agent | 권한·민감정보·외부 입력·부작용 검사 | 실행 전 안전 게이트 제공 |
| Executor Agent | 승인 토큰이 있는 노드만 실행 | 인간 승인과 도구 실행 결합 |
| Verifier Agent | 성공 조건을 실제 결과와 대조 | 답변 생성에서 검증된 완료로 확장 |

Agent Framework는 순차·병렬·조건 분기·실패 복구를 명시적으로 관리한다. 각 에이전트는 구조화된 스키마로 상태를 전달하고, 동일한 `executionId`로 전체 trace를 연결한다.

### 14.7 Azure가 핵심인 이유

| Azure 서비스 | 제품 핵심 역할 | 라이브 증거 |
| --- | --- | --- |
| Azure App Service | Next.js 웹 앱과 API 실행 | 공개 배포 URL에서 전체 흐름 실행 |
| Microsoft Foundry 모델 배포 | 도구 호출과 구조화 출력이 필요한 에이전트 추론 | 배포 모델, 요청 ID, 평가 결과 |
| Azure Cosmos DB | 실행 계약, 목표 그래프, 승인, 검증 영수증 저장 | 새로고침 후 실행 상태 복원 |
| Azure Key Vault | OAuth 자격 증명과 서비스 비밀 보호 | managed identity 접근 구성 |
| Application Insights | 에이전트·도구 단계의 trace, 지연, 오류 관측 | 하나의 `executionId`로 end-to-end trace 조회 |

모델은 구현 전에 도구 호출, 구조화 출력, 지연 시간, 배포 지역, 가용 할당량을 기준으로 선택한다. Azure 리소스 접근에는 연결 문자열보다 managed identity와 최소 권한 RBAC를 우선한다.

### 14.8 해커톤 MVP 범위

100점을 노리려면 기능 수보다 완성도와 실제 증거를 우선한다.

#### 반드시 구현

- 목표, 시간 예산, 허용·금지 행동 입력
- 성공 조건이 포함된 실행 계약 생성
- GitHub PR·이슈 실제 조회
- Outlook 일정 실제 조회 또는 사전 승인된 캘린더 도구 연결
- 의존성 기반 목표 그래프와 실시간 상태 UI
- 드라이런 및 노드별 승인·제외
- 리뷰 팩 생성과 개인 할 일 저장 1개
- 성공 조건 자동 검증과 검증 영수증
- Cosmos DB 실행 복원
- App Service 배포와 Application Insights trace

#### 구현하지 않음

- 범용 브라우저 또는 데스크톱 조작
- 사용자 승인 없는 메일·메시지 전송
- 코드 자동 수정과 병합
- 세 개를 초과하는 외부 업무 도구 연동
- 장기 자율 실행과 백그라운드 감시

### 14.9 UX 원칙

채팅창을 제품의 중심으로 만들지 않는다. 핵심 화면은 사용자가 실행 전후를 빠르게 비교하고 통제할 수 있는 **실행 캔버스**다.

- 상단: 목표, 시간 예산, 성공 조건
- 중앙: 의존성과 상태가 보이는 목표 그래프
- 우측: 선택한 노드의 출처, 도구, 예상 변경
- 하단: 일괄 승인, 선택 제외, 실행 중단
- 완료 후: 성공 조건별 검증 영수증과 절약 시간

모든 상태는 `계획 중`, `승인 필요`, `실행 중`, `검증 중`, `완료`, `조치 필요`처럼 사용자 언어로 표시한다. 실패한 노드만 다시 실행할 수 있어야 하며 전체 레이아웃은 실행 중에도 이동하지 않아야 한다.

### 14.10 생산성 실험

동일한 리뷰 준비 과제를 수동 방식과 OneIntent 방식으로 각각 수행한다.

| 지표 | 수동 방식 기준 | 만점 목표 | 수집 위치 |
| --- | ---: | ---: | --- |
| 완료 시간 | 30분 | 5분 이하 | 실행 타이머 |
| 도구 전환 | 8회 | 2회 이하 | 클라이언트 이벤트 |
| 사용자 조작 | 15단계 | 입력·승인·확인 3단계 | 워크플로 이벤트 |
| 성공 조건 충족률 | 수동 확인 | 100% | Verifier 결과 |
| 근거 연결률 | 불명확 | 100% | 검증 영수증 |

최소 5명이 같은 데이터 세트로 두 방식을 수행한다. 중앙값을 비교하고 원본 이벤트와 계산식을 함께 보관해 심사 시 재현한다.

### 14.11 품질 평가

라이브 데모 외에 10개 이상의 고정 시나리오 데이터 세트로 에이전트를 평가한다.

- 실행 계약 스키마 유효성 100%
- 올바른 도구 선택률 95% 이상
- 주요 주장 근거 연결률 100%
- 성공 조건 판정 정확도 95% 이상
- 금지 행동 차단률 100%
- 전체 성공률 90% 이상
- P95 실행 시간 목표와 단계별 지연 기록

평가 결과와 프롬프트·모델 버전을 연결해 변경 전후 회귀를 확인한다. 실패 사례를 숨기지 않고 유형별로 분류해 개선 결과를 제시한다.

### 14.12 책임 있는 실행

- **계획과 실행 분리:** 모델이 계획을 만들 수는 있지만 승인 토큰 없이는 쓰기 도구를 호출할 수 없다.
- **최소 권한:** 읽기와 쓰기 권한을 분리하고 목표에 필요한 범위만 요청한다.
- **외부 입력 격리:** PR, 이슈, 문서 내용은 데이터로 취급하며 그 안의 지시를 시스템 명령으로 실행하지 않는다.
- **민감정보 보호:** trace와 영수증에서 토큰, 개인정보, 비밀 패턴을 제거한다.
- **멱등성:** 동일한 실행 노드는 중복 할 일이나 일정을 만들지 않는다.
- **복구 가능성:** 실패 노드만 재시도하고 실행 전후 상태를 비교할 수 있다.
- **사용자 통제:** 사용자는 노드별 승인, 제외, 중단, 데이터 삭제를 수행할 수 있다.

### 14.15 구현 우선순위

1. **세로 흐름:** 가짜 UI보다 실제 GitHub 데이터로 목표→계획→승인→실행→검증 한 경로를 먼저 완성한다.
2. **클라우드 증거:** Cosmos DB와 Application Insights를 초기에 연결해 모든 실행이 처음부터 증거를 남기게 한다.

4. **생산성 실험:** 기능 완성 직후 5명 전후 실험을 수행하고 결과를 앱에 표시한다.
5. **평가 회귀:** 고정 데이터 세트로 도구 선택, 근거, 성공 조건, 금지 행동을 자동 평가한다.
6. **시각 완성도:** 마지막에 목표 그래프, 드라이런, 검증 영수증의 정보 밀도와 반응형 동작을 다듬는다.

### 14.16 최종 판단

**OneIntent가 Re:Focus보다 100점 목표에 더 적합하다.** Re:Focus는 “중단 후 복귀”라는 선명한 문제에 강하고 구현 위험이 낮다. OneIntent는 구현 난도가 더 높지만 Copilot SDK, Agent Framework, Azure, 생산성 측정, 안전한 실행, 독창적인 UX가 하나의 필수 흐름에 결합되어 모든 채점 항목의 만점 증거를 만들 수 있다.

다만 해커톤에서 100점에 가까워지는 조건은 기능을 추가하는 것이 아니다. 대표 시나리오 하나를 실제 연동으로 완성하고, 성공·실패·보안·성능을 심사위원 앞에서 재현하는 것이다.

## 15. 진짜 100점 아이디어: First Move

> 매일 아침 하루의 첫 30분을 90초로 컴파일하는 개인 업무 시동 에이전트

### 15.1 검증에서 얻은 결론

[SCORING.md](./SCORING.md) 검증 결과, 100점의 병목은 아이디어의 화려함이 아니라 두 가지였다.

1. **증거 상한:** 구현·측정 증거가 없으면 항목당 배점의 40%가 상한이다. 100점은 모든 항목에서 심사 시점에 검증 가능한 증거가 존재해야 한다.
2. **완성 위험:** 핵심 흐름이 데모에서 실행되지 않으면 기능 완성도가 최대 4점으로 제한된다. 규정상 **완성된 92점 설계가 미완성 100점 설계를 이긴다.**

따라서 진짜 100점 아이디어의 조건은 다음 네 가지다.

- 앱이 동작하는 것만으로 **증거가 자동 생성**된다
- 심사위원이 **자신의 데이터로 라이브 재현**할 수 있다
- 성공 여부를 LLM 감상이 아닌 **결정적 규칙으로 검증**한다
- 외부 연동을 최소화해 **해커톤 내 완성 확률**을 최대로 만든다

### 15.2 추가로 검토한 후보와 기각 사유

| 후보 | 개요 | 강점 | 기각 사유 |
| --- | --- | --- | --- |
| FocusGate | 들어오는 방해 요청을 분류하고 응답·보류를 대행 | 문제 공감대와 RAI 서사 강함 | 메일·메신저 실시간 연동이 필요해 완성 위험이 가장 큼 |
| WeekLedger | GitHub·캘린더 활동을 주간 보고서로 자동 작성 | 증거 수집이 쉽고 완성 위험 낮음 | 유사 제품이 많아 혁신성 5점 만점이 어려움 |
| TimeBank | 캘린더 조각을 모아 집중 블록을 재배치 | 단일 연동으로 구현 단순 | 도구 호출 폭이 좁아 SDK·Framework 25점 증명이 약함 |
| Handoff | 부재·휴가 전 인계 패키지 자동 생성 | 검증 가능한 산출물 명확 | 발생 빈도가 낮아 생산성 반복 측정이 어려움 |

네 후보 모두 특정 영역은 강하지만, 7개 영역 전부에서 만점 증거를 만들 수 있는 조합은 아니었다.

### 15.3 최종안: First Move

**First Move는 OneIntent의 증거 기계를 Re:Focus의 낮은 완성 위험 위에 올린 아이디어다.**

매일 아침 사용자는 `하루 시작` 버튼 하나를 누른다. 에이전트는 밤사이 GitHub 변경과 오늘의 일정 제약을 병렬 수집하고, 오늘의 실행 계약(우선순위 행동 3개, 성공 조건, 금지 범위)을 컴파일한다. 사용자가 드라이런을 확인하고 승인하면 에이전트가 할 일 생성과 이슈 코멘트 초안 같은 안전한 작업을 실행하고, 결정적 Verifier가 성공 조건을 검사해 **증거 영수증**을 발급한다.

```text
아침 07:50 — 하루 시작 버튼
├── Overnight Diff: 밤사이 커밋 3, 이슈 댓글 2, 리뷰 요청 1
├── 오늘의 제약: 회의 2건, 가용 집중 시간 3시간 40분
├── 실행 계약: 우선 행동 3개 + 성공 조건 + 금지 범위
├── 드라이런 승인 (생성될 할 일과 코멘트 초안 미리보기)
├── 실행: 할 일 2개 생성, 이슈 코멘트 초안 1개
└── 증거 영수증: 성공 조건 5/5 통과, 시동 시간 84초, 절약 28분
```

#### OneIntent와의 결정적 차이

| 구분 | OneIntent | First Move |
| --- | --- | --- |
| 트리거 | 임의 목표 입력 (매번 다른 문제) | 매일 아침 동일 시나리오 (반복 측정 가능) |
| 연동 | GitHub + Outlook 필수 | GitHub 필수, 캘린더는 읽기 전용 ICS 옵션 |
| 생산성 증거 | 5명 실험을 별도로 수행해야 함 | 팀원이 매일 쓰는 것만으로 측정 데이터 축적 |
| 완성 위험 | 높음 (이중 연동, 실험 규모) | 낮음 (세로 흐름 1개, 단일 필수 연동) |
| 심사 재현 | 준비된 시나리오 중심 | 심사위원 데이터로 즉석 실행 가능 |

### 15.4 100점을 만드는 4개 장치

#### 장치 1: 증거 자동 생성

모든 실행이 시동 시간, 도구 호출, 근거 링크, 성공 조건 결과를 Cosmos DB와 Application Insights에 기록한다. 해커톤 기간 동안 팀원 4명이 매일 사용하면 심사 시점에 **20회 이상의 실측 데이터**가 쌓인다. 생산성 증거를 발표 자료가 아니라 앱 안의 대시보드에서 직접 보여준다.

#### 장치 2: Judge Mode

심사위원이 임의의 공개 GitHub 저장소 URL을 입력하면 그 저장소의 최근 24시간 변경으로 즉석에서 전체 흐름이 실행된다. "하드코딩된 데모"라는 의심을 원천 차단하고, AGENT4의 재현 불가 감점 조건을 정면 돌파한다.

#### 장치 3: 결정적 검증

Verifier는 LLM 판단이 아니라 규칙으로 성공 조건을 검사한다.

- 우선 행동 3개에 각각 근거 링크가 존재하는가 (URL 검증)
- 생성된 할 일이 실제로 존재하는가 (API 재조회)
- 금지 행동(외부 게시, 메시지 전송)이 실행 로그에 없는가
- 총 시동 시간이 90초 이하인가 (타이머)

검사 결과가 코드 수준에서 재현되므로 심사 AI가 근거를 그대로 확인할 수 있다.

#### 장치 4: 단일 필수 연동

필수 연동은 GitHub 하나다. 캘린더는 읽기 전용 ICS 파일 연결로 대체 가능해 OAuth 이중 연동 실패 위험이 없다. 남는 시간은 기능 추가가 아니라 실패 경로, 관측, UI 완성도에 쓴다.

### 15.5 에이전트 구성

Copilot SDK는 세션, GitHub 도구 호출, 구조화 출력, 진행 스트리밍을 담당하고, Microsoft Agent Framework가 아래 5개 에이전트를 오케스트레이션한다.

| 에이전트 | 역할 | 만점 증거 |
| --- | --- | --- |
| Scout Agent | 밤사이 GitHub 변경과 일정 제약 병렬 수집 | 병렬 fan-out 실행 trace |
| Compiler Agent | 실행 계약과 우선 행동 3개 컴파일 | 구조화 스키마 출력 |
| Policy Agent | 금지 범위·권한·프롬프트 인젝션 검사 | 차단 데모와 감사 로그 |
| Executor Agent | 승인 토큰이 있는 노드만 실행 | 승인 전후 로그 대조 |
| Verifier Agent | 결정적 규칙으로 성공 조건 검증 | 규칙별 통과·실패 영수증 |

오케스트레이션은 `Scout(병렬) → Compiler → Policy → 사용자 승인 → Executor → Verifier`이며, 모든 단계가 하나의 `executionId`로 연결된다.

### 15.6 Azure 구성

추론은 **Microsoft Foundry 모델 배포**로 통일한다(문서 전체에서 이 표기를 사용한다).

| 서비스 | 역할 | 라이브 증거 |
| --- | --- | --- |
| Azure App Service | 웹 앱·API 호스팅 | 공개 URL에서 Judge Mode 실행 |

### 15.7 MVP 범위

#### 반드시 구현

- 하루 시작 버튼과 Overnight Diff 수집 (GitHub 실데이터)
- 실행 계약 컴파일과 우선 행동 3개 제안
- 드라이런 미리보기와 노드별 승인·제외
- 할 일 생성 1종 + 이슈 코멘트 초안 1종 실행
- 결정적 Verifier와 증거 영수증
- 일별 시동 시간·절약 시간 누적 대시보드
- Judge Mode (공개 저장소 URL 즉석 실행)
- Cosmos DB 복원, App Service 배포, App Insights trace

#### 구현하지 않음

- Outlook 양방향 연동 (읽기 전용 ICS로 대체)
- 메시지·메일 전송, 코드 수정
- 다중 사용자 협업 기능
- 사용자별 5명 통제 실험 (일별 실사용 데이터로 대체)

### 15.10 3분 데모

1. **20초:** 첫날 실측한 "아침 시동 30분" 데이터를 보여준다.
2. **30초:** 하루 시작 버튼 → Scout 병렬 수집과 도구 호출 실시간 표시.
3. **30초:** 실행 계약과 드라이런에서 코멘트 초안 노드 하나를 제외하고 승인.
4. **30초:** 실행과 Verifier 규칙 검사, 증거 영수증 확인.
5. **30초:** 누적 대시보드에서 팀원 4명의 일별 시동 시간 추이 확인.
6. **20초:** 심사위원 저장소 URL로 Judge Mode 즉석 실행.
7. **20초:** 인젝션이 심어진 이슈 본문을 Policy Agent가 차단하는 장면.
8. **10초:** 새로고침 복원과 App Insights 단일 trace.

### 15.11 리스크와 대응

| 리스크 | 대응 |
| --- | --- |
| GitHub API 속도 제한 | 조회 캐시와 조건부 요청, Judge Mode는 공개 저장소 읽기 전용 |

| 데모 네트워크 장애 | 직전 실행의 영수증·trace를 로컬 재생 가능하게 보관 |

### 15.12 결론

**First Move를 최종안으로 채택한다.**

- OneIntent의 증거 기계(실행 계약, 드라이런, 결정적 검증, 영수증)를 계승하되, 반복 가능한 아침 시나리오로 좁혀 완성 위험을 Re:Focus 수준으로 낮췄다.
- 생산성 증거가 별도 실험 없이 매일 자동 축적되고, Judge Mode로 심사 시점 재현성을 보장한다.
- 7개 평가 영역 모두에서 만점 게이트가 라이브 데모와 저장소 증거로 연결된다.

100점의 마지막 조건은 문서가 아니라 실행이다: **세로 흐름 완성 → 관측 연결 → 안전 실패 → 측정 축적 → Judge Mode → 완성도**의 순서로 구현한다.
