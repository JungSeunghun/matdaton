# 최종 아이디어: LifeBooking Agent

> 일상에서 반복되는 예약 필요를 먼저 알아채고, 조건에 맞는 후보를 찾아 승인 한 번으로 예약까지 끝내는 생활 예약 에이전트

## 1. 한 줄 요약

기념일 식당, 정기 모임, 반복 출장 숙소처럼 일상에서 되풀이되는 예약을 한 번 등록하면 적절한 시점에 조건을 확인하고 예약 가능한 후보를 찾아, 스마트폰·스마트워치에서 최종 승인한 항목만 실제 예약하는 웹 앱.

## 2. 문제 정의

### 대상 사용자

식당, 숙소, 병원, 미용실, 운동 시설처럼 비슷한 예약을 반복하면서도 매번 검색·비교·입력을 다시 하는 개인 사용자.

### 핵심 문제

사용자는 외식, 정기 모임, 출장과 여행이 생길 때마다 다음을 반복한다.

- 예약이 필요한 날짜를 기억하고 적절한 예약 시작 시점을 계산
- 여러 앱에서 위치, 가격, 평점, 영업시간과 빈자리 검색
- 동행자 취향, 이동 거리, 예산, 취소 정책 비교
- 이름, 인원, 연락처와 요청 사항을 반복 입력
- 예약 확정 내역을 캘린더에 옮기고 변경·취소 기한 관리

기존 예약 앱은 사용자가 필요할 때마다 직접 검색을 시작해야 하고, 캘린더 알림은 “예약해야 한다”는 사실만 알려준다. 예약 필요 감지, 조건 재사용, 후보 비교, 실제 예약, 사후 관리를 하나의 루프로 연결하지 못해 같은 탐색과 입력이 계속 반복된다.

### 해결 가설

반복 일정과 과거 선호에서 예약 필요를 미리 감지하고, 검증된 예약 채널에서 조건에 맞는 후보 3개를 찾아, 스마트워치에서 5초 이내에 선택·승인할 수 있게 하면 예약에 드는 탐색 시간과 입력 단계를 절반 이상 줄일 수 있다.

## 3. 핵심 사용자 흐름

```text
매월 둘째 금요일 — 가족 외식 예약 루틴
├── ① 감지: 다음 금요일 19:00 일정과 4명 예약 필요 확인
├── ② 조건: 집에서 20분, 1인 4만원 이하, 한식, 주차 가능
├── ③ 탐색: 실제 예약 가능한 식당을 여러 채널에서 조회
├── ④ 비교: 거리·가격·평점·빈자리·취소 정책으로 후보 3개 선정
├── ⑤ 승인: 워치에서 1번 예약 / 다른 후보 / 휴대폰에서 상세 보기
├── ⑥ 예약: 선택한 식당에 4명 예약, 확정 번호와 취소 기한 재조회
└── ⑦ 관리: 캘린더 등록, 전날 알림, 탐색 8분·입력 6단계 절약 증명
```

숙소 예약은 반복 출장 일정을 감지해 회사 근처, 숙박비 상한, 조식, 무료 취소 조건으로 후보를 찾는 두 번째 시나리오로 둔다. 사용자의 기본 조작은 **예약 필요 알림 → 후보 선택·최종 승인 → 예약 확정 확인**의 3단계로 고정한다. 상세 비교와 조건 수정은 웹 앱, 빠른 선택과 승인은 스마트폰·스마트워치가 담당한다.

## 4. 에이전트 설계

### GitHub Copilot SDK

- “매월 둘째 금요일 가족 외식 예약” 같은 자연어 예약 루틴 생성·수정
- 날짜, 인원, 위치, 예산, 선호, 제외 조건과 취소 가능 기한 확인
- `create_booking_routine`, `search_availability`, `compare_options`, `request_booking`, `get_booking_status` 앱 도구 호출
- 후보 탐색, 가격·정책 비교, 승인 대기, 예약 확정 이벤트를 웹 UI에 스트리밍
- 사용자 최종 승인 이후에만 실제 예약 도구 호출
- Copilot 세션 ID를 Agent Framework 실행 ID와 연결

### Microsoft Agent Framework — 5개 에이전트 오케스트레이션

| 에이전트 | 역할 | 만점 증거 |
| --- | --- | --- |
| Preference Agent | 과거 선택과 이번 요청에서 예약 조건·금지 조건 정리 | 출처가 있는 구조화 선호 프로필 |
| Discovery Agent | 공식 예약 API에서 빈자리·객실과 최신 가격 병렬 조회 | 제공처별 fan-out trace와 조회 시각 |
| Comparison Agent | 거리·가격·평점·정책을 사용자 가중치로 비교 | 후보별 점수 근거와 탈락 사유 |
| Booking Agent | 최종 승인 토큰과 동일한 조건으로만 예약 실행 | 승인 전후 요청 hash와 API 로그 |
| Verification Agent | 예약처를 재조회해 확정 번호·금액·취소 기한 검증 | 제공처 응답 기반 예약 증명서 |

```text
Preference → Discovery(병렬) → Comparison → 기기별 최종 승인
→ Booking → Verification
```

예약 필요 시점 계산, 중복 방지, 정책 차단, 기기 선택, 결제 한도와 지표 계산은 AI 판단이 필요 없는 결정적 서비스로 구현한다. 모든 단계는 하나의 `runId`로 연결한다.

## 5. 100점을 만드는 4개 장치

1. **Reservation Memory** — 매번 다시 입력하던 인원, 지역, 예산, 음식·객실 선호, 알레르기, 주차, 무료 취소 조건을 루틴별로 기억하고 이번 예약에서 바뀐 값만 묻는다.
2. **Slot Watch** — 예약 오픈 시각이나 원하는 날짜를 미리 계산해 자동 검색하고, 자리가 없으면 사용자가 정한 기간 동안 재조회하되 과도한 호출 없이 상태 변화를 알린다.
3. **Watch Approval** — 사용자가 앱을 찾아 열지 않아도 워치에서 후보 선택·승인·보류 중 하나를 5초 안에 처리한다. 가격이나 취소 조건이 바뀌면 기존 승인을 폐기한다.
4. **Booking Proof** — 예약 API를 재조회해 확정 번호, 최종 금액, 인원, 날짜, 취소 기한을 검증하고, 절약한 탐색·입력 시간까지 하나의 예약 증명서로 발급한다.

## 6. Azure 아키텍처

추론은 **Microsoft Foundry 모델 배포**로 통일한다.

| 서비스 | 역할 | 라이브 증거 |
| --- | --- | --- |
| Azure App Service | Next.js 웹 앱·Copilot SDK 서버 호스팅 | 공개 URL에서 예약 제공처 데모 실행 |
| Azure Functions | 예약 필요·오픈 시각 감지와 Slot Watch 실행 | 예정·실제 검색 시각 로그 |
| Azure Service Bus | 검색·예약 실행 전달, 재시도, DLQ | 중복 메시지와 실패 복구 데모 |
| Azure Container Apps | Agent Framework API·예약 worker 실행 | 5개 에이전트 실행 trace |
| Microsoft Foundry 모델 배포 | 선호 구조화와 후보 설명 생성 | 모델 배포명과 요청 추적 |
| Azure Cosmos DB | 예약 루틴, 선호, 실행, 승인, 증명서 저장 | 새로고침 복원과 예약 이력 |
| Azure Key Vault | 예약 제공처 자격 증명과 Push 비밀 보호 | managed identity 구성 |
| Application Insights | `runId` 기반 end-to-end 관측 | 단일 trace에서 전체 단계 확인 |

스마트폰은 PWA Web Push를 수신한다. 스마트워치는 페어링된 스마트폰의 알림 미러링을 우선 활용하며, 가격·취소 조건의 상세 확인이 필요하거나 운영체제가 액션을 전달하지 않으면 휴대폰 승인 화면으로 연결한다.

## 7. MVP 범위

### 반드시 구현

- 자연어로 “매월 둘째 금요일 4명 가족 외식” 예약 루틴 생성·활성화
- 날짜·인원·지역·예산·선호·알레르기·주차·취소 조건 저장
- 실제 시간 기반 예약 검색과 `routineId + targetDate` 중복 방지
- 공식 API 사용 권한을 확보한 식당 예약 제공처 1곳의 실시간 빈자리 조회
- 조건에 맞는 후보 3개와 가격·거리·평점·취소 정책 비교
- 최종 요청 hash를 보여 주는 드라이런과 승인 후 실제 예약 1건 생성
- 모바일 PWA Push와 워치 알림 미러링 폴백
- 예약 API 재조회 기반 확정 검증과 Booking Proof
- Before/After 누적 대시보드와 예약 제공처 sandbox 데모 모드
- Cosmos DB 복원, Azure 배포, App Insights trace

### 구현하지 않음

- 공식 API나 제휴 권한이 없는 예약 사이트의 화면 자동 조작
- 사용자 승인 없는 예약·결제·취소·변경
- 여러 식당·숙소 플랫폼을 동시에 지원
- 숙소 실제 결제와 환불 불가 상품 예약
- 네이티브 iOS·Android·watchOS·Wear OS 앱 동시 개발
- 10회 미만 표본으로 확정적 향상률 주장

숙소 예약은 MVP 이후 같은 `BookingProvider` 계약으로 추가한다. 공식 API에서 객실 재고, 세금 포함 최종가, 무료 취소 시각을 확인할 수 있을 때만 자동 예약을 지원한다.

## 8. 생산성 측정

| 지표 | 수동 기준 가설 | 목표 | 수집 방식 |
| --- | ---: | ---: | --- |
| 후보 탐색·비교 시간 | 15분 | 2분 이하 | 검색 시작부터 후보 승인까지 타이머 |
| 입력·화면 전환 단계 | 12회 | 3회 이하 | 웹·폰·워치 이벤트와 도구 호출 |
| 원하는 조건 충족률 | 60% | 90% 이상 | 필수 조건을 만족한 확정 예약 비율 |
| 예약 성공률 | 측정 필요 | 95% 이상 | 승인된 요청 대비 확정 번호 발급 비율 |
| 승인 조건과 실제 예약 일치율 | 측정 필요 | 100% | 요청 hash와 제공처 재조회 결과 비교 |
| 승인 없는 예약·결제 | 0건 | 0건 | 정책·예약 API 감사 로그 |

수동 기준값은 해커톤 첫날 팀원들이 같은 식당 조건으로 직접 검색·비교·예약해 확정한다. 실제 개선율은 다음과 같이 계산한다.

```text
예약 소요 시간 개선율 = (Before 중앙값 - After 중앙값) / Before 중앙값 × 100
순 절약 시간 = Before - After - 설정 시간 - 검토 시간 - 복구 시간
조건 충족률 변화 = After 충족률 - Before 충족률 (%p)
```

최소 2주 또는 동일 루틴 10회 전에는 “데이터 수집 중”으로 표시한다. 평균만 제시하지 않고 중앙값, 표본 수, 관찰 기간, 제외 사유와 원본 이벤트를 함께 보존한다.

## 9. 책임 있는 AI·보안·신뢰성

- 빈자리·객실 조회와 후보 비교는 사용자가 허용한 제공처에서만 자동 실행
- 실제 예약·변경·취소·결제는 날짜, 인원, 대상, 최종 금액, 취소 정책 단위 승인 필요
- MVP 결제는 제공처 sandbox 또는 현장 결제 상품으로 제한하고 카드 정보를 저장하지 않음
- 가격, 세금, 수수료, 환불·취소 조건이 승인 후 달라지면 실행을 중단하고 재승인
- 워치와 잠금 화면에는 연락처, 동행자, 상세 일정 같은 민감 정보를 표시하지 않음
- 모델은 후보를 설명할 뿐 예약 가능 여부와 가격은 공식 API 응답만 신뢰
- 비밀은 Key Vault, 서비스 접근은 managed identity와 최소 권한 RBAC
- 검색, 예약, 변경, 취소에 각각 멱등성 키를 적용해 중복 실행 방지
- 예약 사이트의 이용약관과 자동화 정책을 준수하고 공식 API 없는 화면 자동화는 금지
- timeout, 최대 2회 재시도, Service Bus DLQ, 실패 단계별 복구 제공

## 11. 3분 데모

1. **20초:** 수동 식당 예약의 탐색 시간·입력 단계 Before 원시값 제시
2. **20초:** “매월 둘째 금요일 4명, 한식, 1인 4만원” 예약 루틴 생성
3. **30초:** 예약 제공처에서 실제 빈자리를 병렬 조회하는 Agent Framework trace
4. **30초:** 거리·가격·평점·취소 정책 후보 3개를 워치 화면에서 선택·승인
5. **30초:** 공식 API 예약 후 확정 번호·금액·취소 기한 Booking Proof 확인
6. **20초:** 가격 변경 시 기존 승인을 폐기하고 재승인하는 안전 데모
7. **20초:** 중복 메시지에도 예약이 하나만 생성되는 멱등성 및 Before/After 확인
8. **10초:** 새로고침 복원과 Application Insights의 단일 `runId` trace

| 식당·숙소마다 데이터 형식이 다름 | 공통 `BookingProvider` 계약과 제공처별 adapter로 격리 |
| 스마트워치별 Web Push 액션 차이 | 가격·정책 상세를 모바일 PWA에서 재확인하도록 폴백 |
| 예약 실행이 중복 전달됨 | 예약 요청 hash와 제공처 idempotency key를 함께 적용 |
| 알림이 많아져 방해가 됨 | 조용한 시간, 일일 상한, 자동 묶음, 루틴별 일시정지 제공 |
| 승인 후 가격·재고가 바뀜 | 예약 직전 재조회하고 차이가 있으면 실행 중단과 재승인 |
| 취소·환불 피해 발생 | MVP는 현장 결제·무료 취소 상품으로 제한하고 기한 전 알림 |
| 실측 표본이 부족함 | 첫날 수동 기준선 수집, 팀 실사용, 10회 미만은 추세만 표시 |
| Azure 또는 제공처 장애 | 제한된 재시도, DLQ, 부분 결과 저장, 수동 예약 링크 제공 |

## 13. 구현 순서

1. 제공처 검증: 식당 예약 공식 API·sandbox 권한, 실제 예약·조회·취소 범위 확인
2. 기술 검증: Copilot SDK 예약 도구, Agent Framework 구조화 출력, 모바일 Push 확인
3. 세로 흐름: 예약 루틴→빈자리 탐색→비교→승인→예약→재조회 검증 완성
4. 클라우드 증거: Cosmos DB와 Application Insights를 초기부터 연결
5. 안전 실패: 가격 변경 재승인, 멱등성, timeout, 재시도, DLQ
6. 측정 축적: 수동 기준선과 실행별 Booking Proof 자동 기록
7. 기기 UX: 모바일 상세 비교와 워치 빠른 승인 폴백 완성
8. 숙소 확장: 공식 API 권한 확보 후 같은 provider 계약으로 무료 취소 상품 지원
